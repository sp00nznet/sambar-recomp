# Architecture

Three parts, all in one 32-bit process (`build\sambarrecomp.exe`):

| Part | Where | Owns |
|---|---|---|
| The lifted server | `src/recomp/gen/<module>/` (generated by `run_lift.py`, gitignored) | every function of the six modules below as C, one `recomp_XXXX.c` per 400 functions, plus `recomp_dispatch.c` over all of them for indirect calls |
| The host | `src/runtime/host.c` | the module table, the guest's command line (`ntserver.exe -d`), the fault report and the watchdog |
| The runtime | pcrecomp `runtime/native32` (`native32.c`, `modules32.c`), `runtime/recomp32` | the image loader, import binding, the module loader, threads, and the bridge between lifted code and real Windows |

## The modules

Sambar is a small front end on a large DLL. `ntserver.exe` is the NT service
wrapper; with `-d` it runs the same server in a console instead, which is how
the recomp runs it (no service install, no window). `server.exe`, the tray
icon front end, is not lifted.

| Module | Linked at | Mapped at | Functions | What it is |
|---|---|---|---|---|
| `ntserver.exe` | 0x00400000 | 0x00400000 | 342 | service / console front end |
| `sambar.dll` | 0x10000000 | 0x10000000 | 10,419 | the server: HTTP, FTP, proxy, mail, DNS, the scheduler, `.stm` pages |
| `sambarcm.dll` | 0x10000000 | 0x10400000 | 3,564 | common library: memory, hashing, sockets, IMAP client, crypto |
| `sambarcs.dll` | 0x10000000 | 0x10600000 | 1,519 | its scripting engine |
| `sqlite3.dll` | 0x10000000 | 0x10700000 | 1,338 | SQLite 3 |
| `samples.dll` | 0x10000000 | 0x10800000 | 202 | the sample plug-in that `config.ini`'s `[user-events]` load |

Every DLL is linked at 0x10000000. Windows relocates them at load time; a
static recompilation cannot, because the lifted C has every absolute address
in it. So `tools/catalog.py` first runs pcrecomp's `tools/pe/rebase.py`, which
applies each DLL's relocations to a copy in `work\rebased\` at its own base,
and everything after that (catalog, lift, run) works on the copies. The host
maps the copies; `GetModuleFileName` still reports `game\bin\<module>`, so the
server finds its folder, its `config\` and its `docs\` where they are.

The DLLs Sambar ships but this configuration never loads (`sambardb.dll`,
`sambarje.dll`, `sqlite2.dll`, OpenSSL's `libeay32.dll` and `ssleay32.dll`)
are not lifted. Turning on the DBMS, the Java engine or SSL would load the
original binary natively. See [ROADMAP.md](../ROADMAP.md).

## Data flow

1. `tools/catalog.py` rebases the six modules and runs `disasm32.py` on each,
   seeded with the function addresses from Sambar's own linker MAP files
   (`bin\*.map`, shifted by each module's rebase delta). `sqlite3.dll` has no
   MAP.
2. `run_lift.py` lifts each module into `src/recomp/gen/<module>/` and writes
   one dispatch table over all of them. It refuses an `ntserver.exe` or
   `sambar.dll` whose PE stamp is not 6.4p's.
3. At run time the host maps the six copies, binds their imports (Windows
   DLLs natively, guest-to-guest imports to the lifted exports, the loader's
   calls to `modules32.c`), runs each DLL's `DllMain` after the guest modules
   it imports, and enters `ntserver.exe`'s entry point.
4. `sambar.dll` reads `config\config.ini`, opens its listening socket, and
   `LoadLibrary`s `samples.dll` for its plug-in hooks. `modules32.c` answers
   that from the table (the lifted copy, attached on first load) instead of
   loading the original file.

## Threads, sockets, CGI

Nothing here is special-cased: these are all real Windows calls through
native32's bridge.

- **Threads.** Sambar runs a pool of worker threads (`Idle Threads = 10`)
  plus the scheduler and DNS. A thread Windows starts on a guest address faults
  on the non-executable guest code, native32's handler moves it to a
  trampoline, and the lifted body runs on a fresh guest stack. One machine lock
  covers the lifted register file. It is released around every native call,
  so a thread blocked in `accept`, `select`, `recv` or `Sleep` does not hold
  up the others.
- **Winsock.** `ws2_32` is called directly. The listening socket is bound to
  whatever `Force IP Bind` says (`127.0.0.1` in the harness and the Setup
  config).
- **CGI.** `/cgi-bin/*.pl` runs the bundled `perl\perl.exe` as a child
  process (`CreateProcess`, pipes). That child is the original Perl, not
  lifted. It is outside the server, as it would be under Apache.
- **The registry, the event log.** `ADVAPI32` natively. In `-d` mode the
  server writes no service keys.

## The conformance check

`tools/http_diff.py` runs the original `ntserver.exe -d` and then the recomp
on `127.0.0.1:18080` and `:18081`, one at a time: with one Sambar running, a
second one (two originals included) accepts connections and never answers
them, likely over the single-instance pipe `\\.\pipe\SambarServer` that
`-d` opens for its display. It waits 5 s after the port opens, because the
listening socket comes up before the plug-ins' `INIT` hooks have run, and a
request in that window waits on them. Each gets its own copy of `game\`
and a `config.ini` generated from `config.bkp`, and both serve one generated
docroot with fixed file times. The same corpus of raw HTTP requests goes to
each, and the responses must match byte for byte after the `Date` header is
dropped and each server's port and folder are replaced by placeholders.
